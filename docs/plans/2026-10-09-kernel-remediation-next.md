## 内核维护顺序

维护优先处理已定位的问题，保留当前事务和未知效果保证。验证范围跟随实际代码变动及授权，不把平台缺口混入核心缺陷，也不默认重跑全库；静态审查不能代替运行行为接受。

| 顺序 | 工作与范围 | 完成条件 |
| --- | --- | --- |
| 1 | RPC 深度、Unicode/id 与响应序列化修复已实施 | 解码递归限制和不可编码字符串转成解析失败；id 按冻结正则回显；编码失败有稳定兜底。仅静态审查、未行为验证；本轮不运行测试或探针 |
| 2 | knowledge 在 G2-K 开放前收口 | 核验可信人类决定与 subject/target，检查完整 scope；共享写入前持久 claim，重复调用只重放或观察 |
| 3 | 使用当前入口文档 | 区分注册命令与 provider 可用性、只读 API 与 RPC、隔离恢复与离线替换、源码运行与安装包分发 |
| 4 | 后续代码改动的证据 | 有新授权的验证范围与独立接受依据，原始失败/输出另存，不重建历史验收文件 |
| 5 | 用户已授权修复后更新文档并提交/推送 main（REQ-RPC-05） | 普通提交和推送，合并已有远端 main 历史，核对远端实际 ref；实际结果以修复任务及对应同步记录为准 |

文件分工按实际维护任务确定，不沿用已结束的代理编组。冻结契约、历史轮次和签字保持不可变；后续证据使用新目录。

## Provider 与项目数据

内核保留项目身份、权限、幂等事务、不可变引用与摘要、审批和未知状态规则。provider 承担已配置的外部执行、环境、交付、归档与恢复效果；配置来自部署需要，安全规则不是可关闭开关。停用能力不删除已落盘事实，也不解除审批或项目限制。`initialize` 公布注册入口，核心命令是否可执行仍取决于 provider；没有注册的可选功能不公布。

查询和记录需要继续区分不可变版本、当前索引和派生展示。错误参考保存发生条件、关联 attempt、修复及重验结果；没有历史事实时报告 unavailable。测试资料与业务资料分离，旧歧义来源游标只能重新证实或隔离，不能猜测身份。
