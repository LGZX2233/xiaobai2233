# 可复用方法的成长与复核

文档版本：1.1.0；更新日期：2026-10-12（Asia/Shanghai）。本文定义项目 agent skill 的提炼、复用评价和修订方法，适用于技术工作流程及面向用户的文档方法。入口是 [kernel-grow-skills](../../.agents/skills/kernel-grow-skills/SKILL.md)，当前版本与证据见 [skill registry](../records/skills/registry.json)。原需求见[成长要求](../requirements/2026-10-10-clean-layout-and-skill-growth.md)，本次评分范围和失败分析补充见 [REQ-BOUNDARY-04/05](../requirements/2026-10-12-kernel-boundaries.md)。

这是仓库文档工作流，没有接入内核运行、provider、knowledge scoring 或自动监听。系统 `skill-creator` 是编写初版时采用的外部 Codex 创作指南，不属于已启用的内核能力。文档版本、skill 版本和运行内核业务 revision 分别管理；建立时的源码基准为 `0a619766162682606ad57a9aa4c1926d54c1b891`，当时 skill 文档尚未提交。方法版本与实际观察以索引为准，不因提交文档而视为行为验证。

## 什么时候提炼

真实重复工作中，有一个稳定的判断方法或资源能减少重新探索、错误或认知负担时，可以提炼 skill。用户明确要求可复用方法时，可依据具体目标先建立试用版本，不必为了满足次数而虚构重复成功。只有任务结果、通用常识或尚不清楚适用前提时，先保留任务记录或候选方法。预计复用收益不足以抵消维护成本时，保持普通文档即可。

提炼前写清任务与读者目标、前提、适用范围、不适用范围、已知反例和失效因素。反例是一个在声称的适用范围内出现相反结果的真实观察；假设案例应标明假设，不能成为成功或失败证据。成功也要检查是否依赖额外人工修正、偶然环境或技能以外的工具，避免把结果归功于未经区分的方法。

面向用户的文档可评价读者是否能找到答案、理解概念和完成目标，内容顺序按读者目标决定。可追溯资料和交接清单各有用途，但每篇文档不必使用同一套标题或证据表。用户的阅读反馈评价文档方法，不建立用户能力分数；学习画像继续遵循[描述式记录规则](continuous-records.md)。

## 每次复用怎么记录

调用前从 registry 选当前版本，确认请求符合 scope 和 prerequisites，并检查是否存在待复核问题或失效因素。`review_required` 版本先处理已知问题；只有明确不受该问题影响、且原有授权覆盖的场景才可有限观察，并记录理由。`suspended` 版本停止按原方法复用，待修订或复核决定；阅读其历史记录不等于恢复使用。版本名称、用户当前要求和调用结果都不能由摘要推断。

每次实际复用后，使用[评估模板](../records/skills/assessment-template.md)保存请求摘要、skill ID/版本、来源、适用判断、结果、四个分维度评价、反例或限制，以及后续决定。记录应简短到足以支持下一次判断；同一任务的真实证据由任务主记录拥有，评估引用它，不复制整份日志。未调用 skill 的本轮静态改写属于修订记录，不伪装成复用成功。

来源注明实际可确定的日期、输入版本、工作树范围或用户反馈。没有对话 ID 时可以写“2026-10-10 当前会话用户反馈”，不得补造 ID。源码 `source_revision` 不等于尚未提交 skill 的精确版本；对这类版本同时说明文件路径、registry 分配的版本标签和对应修订记录。

## 评价什么

分数评价方法在这次任务中的表现，不评价用户。使用有限的 `0`、`1`、`2` 与 `null`；各维度的含义不同，不取平均、不制造万能总分。每个非空分数附具体证据和限制；反馈能证实存在问题却不足以确定程度时，保留文字反馈和 `null`。

| 维度 | 0 | 1 | 2 | null |
| --- | --- | --- | --- | --- |
| `correctness` 正确性 | 方法导致实质错误或违反已确认要求 | 结果可用但需要有证据的局部纠正 | 观察范围内结果符合要求且无需实质纠正 | 未观察或证据不能支持分值 |
| `applicability` 适用性 | 声称适用但关键前提不成立或选错方法 | 适用条件有歧义，需要额外判断 | 记录的适用条件明确覆盖本次场景 | 缺少适用观察 |
| `reuse_benefit` 复用收益 | 相较明确对照增加工作或没有预期收益 | 有局部收益，但仍需明显人工补充 | 有证据显示减少重复工作、错误或读者理解负担 | 无可靠对照或收益证据 |
| `maintainability` 可维护与可读性 | 内容过重、过时或维护成本使本次使用难以继续 | 有可识别的维护或阅读成本，仍可使用 | 本次可用内容精简、容易维护和读取 | 未观察维护或读取成本 |

四个维度均以 `2` 表示本次观察良好，`maintainability` 同时考虑维护与阅读的认知负担。阅读时间、找答案的过程或用户明确反馈可以支持文档评价；不要根据用户问过一个问题推断其长期知识程度。缺少对照时不把“看起来更清晰”写成复用收益已经证实。

## 数据处理接口与评分范围

这里的接口是记录输入、评估输出及复核的文档约定，不是新增 RPC 或可执行服务。数据处理者读取具体 skill 版本的 scope、请求、实际结果及证据，输出[评估记录](../records/skills/assessment-template.md)和必要的修订建议；只有实际调用才能形成调用观察。尚未调用、只有编辑或静态推断时，记录修订或发现，不能假装成功/失败使用。

每次评估的单位是 `(skill_id, skill_version, 本次请求与前提, 来源版本, 观察范围)`。不同版本、任务、环境或验证深度的分数不能默认合并；没有观察的维度为 null。环境/provider 故障或用户取消不自动证明方法正确性为 0；应分别评价方法是否在证据范围内正确处理该情况。范围误用仍需分析是谁声明或忽略了前提，不默认归责用户。

四维评分不用于交付验收、批准、执行路由、重试、权限、自动晋升或训练奖励，也不自动调用 KnowledgeService。知识 `ScoreEngine` 的 use/outcome 反馈加权及衰减是另一机制；当前 `KnowledgeService.score` 聚合项目反馈，不能当成某个 skill 的四维质量分或用户水平。用户画像只记录可纠正的描述。

输入缺少精确版本、关键证据或适用前提时，输出缺口和未决问题；不要填默认分数。评估记录可供人或后续数据处理者选择修订，但不改变运行状态，不发起 provider 写入，不凭低分调用执行命令。对应源码与能力位置见 [K-KNOWLEDGE](../modules/nodes/knowledge.md)；训练消费边界见[训练数据职责](training-data-boundary.md)。

## 调用失败的分析与总结

失败分析适用于实际 skill 使用未达到目标，以及使用期间相关工具/provider/RPC 出错；记录必须说明是哪一种失败。静态风险、假设和转述的旧评价另列，不能登记为已复现调用失败。错误码只是症状，不是根因。一次调用包含多个阶段时，逐个标出已成功、失败及未知部分。

| 分析项 | 必须回答的问题 |
| --- | --- |
| 现场与适用性 | 请求、预期/实际、skill/工具版本、输入范围、环境和前提是什么？是否符合声明 scope？ |
| 阶段与时间线 | 失败在选择、解析/校验、持久意图、外部效果、观察、结算还是记录阶段？实际调用顺序是什么？未知时间不补造。 |
| 可追踪证据 | 原错误/堆栈与来源在哪里？有哪些回执、operation_id、事实水位和可确定的状态？仅保存与排障必要的非敏感信息。 |
| 因果分析 | 候选原因有哪些？各自的支持、反证和已排除条件是什么？哪些属于环境/provider 而非方法？未验证假说明确标记。 |
| 根因及缺口 | 哪些原因已确认？若未知，缺少何种证据、由谁或什么后续观察能区分候选原因？ |
| 影响与恢复 | 哪些输出、记录或外部效果受影响？是否需要纠正/撤回？效果未知时先观察已有结果，不能假定未执行。 |
| 修正与复验 | 方法修订、范围收窄或调用纠正是什么？是否具备重试授权及安全状态？哪些检查实际运行、结果如何、哪些未运行？ |

总结至少保留“失败阶段与症状；已确认原因/未决原因；影响；修正；复验状态”，并链接主证据。分析完整指覆盖这些问题，不要求凭空得到确定根因；原因未知时不得把编辑完成写成问题解决。针对每个未决原因留下具体后续观察问题，并按证据更新总结。

原因类仍使用下表四种方法复核类别，可组合或未确定；实际操作的网络、宿主配置、provider、输入数据及存储原因另作文字记录。失败历史和原回执保留，修订另建版本。任何分析或评分都不授权重放未知外部写入；复验是否执行遵从当前任务授权与限制。

## 低分、反例与修订

起始建议是：任何维度为 `0` 或出现实质反例时进入 `review_required`；重复出现 `1` 时检查是否有同一问题。不是固定的永久阈值，评估记录可以按任务风险、读者目标和证据成本调整触发条件并说明原因。明确反馈指出要求缺失时，即使分数均为 `null`，也可直接触发复核。涉及正确性的实质失败可以暂停该版本，一次成功不能抵消未解决的问题。

| 原因分类 | 判别问题 | 修订方向 |
| --- | --- | --- |
| `method_defect` 方法问题 | 前提成立且正确调用仍产生错误吗？ | 修正必要步骤或决策条件；严重时暂停该版本 |
| `scope_mismatch` 范围问题 | 方法声称的适用范围过宽或缺少关键前提吗？ | 收窄 description、scope 或 prerequisites |
| `stale_assumption` 过期问题 | 来源、工具、环境、读者需求或版本已改变吗？ | 更新引用与失效条件，重新观察相关场景 |
| `caller_misuse` 调用误用 | 调用者忽略明确前提、跳过必要判断或超出授权吗？ | 修正调用选择；若提示容易误读，同时改善 skill 的指引 |

原因可以组合，也可以暂未确定；先保留原始观察，再形成解释，不把调用误用当成掩盖方法问题的默认答案。反例应写清范围和后果，成功记录也写清尚未覆盖的场景。

复核形成明确链路：评估或反馈 → `review_required` / 必要时 `suspended` → 带依据的修订记录 → 新版本 `trial` / `not_validated` → 在获授权的实际适用场景重新观察 → 复核决定。修订记录引用旧版本和原问题，说明改了什么、哪些不确定性仍存在，以及哪些后续观察可以判定改善。变更完成可以关闭编辑事项，不能关闭尚未观察的效果问题。

当相关正向观察和反例处置足以支持明确 scope，复核者可把版本改为 `active` / `scope_supported`，记录判断依据及仍未覆盖的场景。所需证据量随风险调整，不强制所有方法达到同一次数。新反例、来源失效或需求变化可重新打开复核；证据撤回时同步撤回依赖它的结论。退役用 `retired` 保留替代入口，纠正或用户要求删除的资料遵循[持续记录修订规则](continuous-records.md#修订撤回与删除)。

## 最小索引与状态

[registry.json](../records/skills/registry.json) 只拥有方法目录、版本状态和引用，不拥有运行注册，也不保存用户分数。JSON 路径以项目根目录为基准；评估 Markdown 链接以文件所在目录为基准。

| 字段 | 含义 |
| --- | --- |
| `schema_version` / `updated_at` / `timezone` | 此文档索引格式版本与实际维护日期 |
| `skill_id` / `path` / `current_version` | 稳定名称、SKILL 路径和当前文档版本标签 |
| `versions[].version` / `status` | 独立版本和 `candidate`、`trial`、`active`、`review_required`、`suspended`、`retired` 状态之一 |
| `validation_status` | `not_validated`、`limited_evidence` 或 `scope_supported`；仅说明所列 scope 的证据程度 |
| `source_revision` / `source_worktree` | 引用的源码基准与文档工作树说明，不冒充已提交 skill 的摘要 |
| `scope` | `applies_to`、`prerequisites`、`exclusions` 三个简短列表 |
| `review_refs` / `evidence_refs` | 复核/修订记录与实际观察来源；空列表表示尚无相应证据 |

评估记录用稳定 `record_id`、递增 `record_version`、日期、来源、skill ID/版本、记录状态和四维分数定位。`null` 及未验证状态保留未知，修订引用替代内容；模板不是一条实际评估。skill 的未知项可以渐进补足，不靠增加永久禁令覆盖所有假设例外。

## 授权与当前边界

常规评估和项目记录维护使用当前任务已有授权，不反复询问同一权限。重要动作如发布、推送或重要数据删除以用户明确审批为准，先核对会话已有授权是否覆盖动作及其条件；已有批准继续有效。缺少批准时先完成可审查的准备工作，在实际执行前交由用户最终审批。skill 本身不能授权外部操作或扩大任务范围。

验证遵循当前任务限制。用户要求不测试时，只核对文档链接、元数据及差异，不启动测试、行为 probe 或运行验证。本轮新版本均保留 `trial` / `not_validated`；后续实际观察需已有授权覆盖，否则先说明需要的验证再取得授权。当前没有运行插件、核心知识评分或自动晋升机制。
