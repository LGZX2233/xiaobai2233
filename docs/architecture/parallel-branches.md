# 并行分支、多方案包与收敛

文档版本：1.1.0；更新日期：2026-10-12（Asia/Shanghai）。源码依据：`16410c9fbf4a8507445b4603e371e701614e4499`。归属 [K-EXECUTION](../modules/nodes/execution.md)，对应 [REQ-BOUNDARY-08](../requirements/2026-10-12-kernel-boundaries.md)。状态为设计说明及静态核对，未实现分支对象、方案评分或模块收敛命令，`release_approved=false` 不变。

## 需求原话与拆解

用户要求：执行模型允许多方案尝试、打包为模块、测试时对不同实现评分并提交为包，**即使不使用也有保存入库的可能**；收尾来验收并入主库。

拆成四项需要内核留存与宿主编排共同支撑的要求：

1. 一次分发可产生**多条并行分支**，每分支独立执行、独立产物；
2. 分支产物聚合为**方案包**（可提交、可比对、可评分）；
3. 方案包之间**评分与比较**供收敛参考；
4. 收敛选定的进入项目正式采用流程；**未采用的方案包也可留存入库**，保存不等于正式采用，具体留存规则仍待设计。

设计模型分发前需固定模块架构、拆分需求、执行范围和验收标准，并引用项目整体约束。每个执行模型可在分配范围内尝试多种实现，提交测试依据与方案包；多分支与多方案不是一一对应关系，一个分支可以顺序产生多个包。收尾模型比较实现、验收并整理模块依赖，按已选择的[路线 A](model-review-identity.md)提交纳入建议，由人类确认最终采用。

并行模块与同一模块的替代实现是两个维度。候选选择以模块为单位：同一模块可选择一个实现，或在明确兼容条件下组合多个实现；不同模块可共同纳入。项目收尾需固定采用的包清单并进行集成验收，不能把整个项目的所有分支强制视为只能选一包的竞争关系。多包组合的规则尚未实现。

## 现状与差距

| 要求 | 现状 | 差距 |
| --- | --- | --- |
| 并行分支 | `attempt` 和 `execution_root` 保存任务/策略隔离；目录规则拒绝重叠，不是全局并发禁令 | 无显式分发对话、分支归属与汇合对象，现有机制不能代表完整并行拓扑 |
| 方案包 | packet 包含多策略；archive 可导出 manifest 与 artifacts | 尚无模块方案包及其架构/需求基线关联 |
| 评分比较 | `attempts_compare` 提供尝试、验证与消耗的只读比较 | 未实现按版本化标准对不同实现评分；knowledge 的 `ScoreEngine` 计算知识使用/结果事件分数，不是方案评审器 |
| 未采用也入库 | 不可变账本保留失败等过程，archive 提供制品留存基础 | 未定义候选包留存政策和项目正式采用记录 |

## 提议的结构（技术方案，待决策）

以下是候选方案，非既定实现。

### 结构与命名

- **`execution_branch`**：一次分发下的执行分支。字段候选：`branch_id`、`task_ref`、`dispatch_ref`、`module_baseline_refs`、`scope_ref`、`acceptance_refs`、`root_ref`、`status`。分支可关联多次 attempt 与多个实现；重试仍创建新 attempt，多层分支嵌套另待决策。
- **`solution_package`**：某种实现的固定提交。字段候选：`package_id`、`branch_ref`、`module_baseline_refs`、`attempt_refs`、`artifact_refs`、`package_digest`、`verification_refs`。修订产生新包或新版本，不能覆盖被评分引用的字节。
- **`implementation_review`**：数据处理侧的评分审阅记录。字段候选：`package_ref`、`rubric_ref`、`evaluation_refs`、`score`、`limitations`、`reviewer_role`、`review_ref`。形式尚未定，不混入知识使用分数或 skill 方法评价。
- **`branch.converge`**：显式收敛操作候选。入参包含按模块分组的选定包清单、精确基线、模块及集成验收与审阅依据、人类确认和 `expected_heads`；产物为项目采用记录或交付准备记录。机器可准备提案或执行已授权操作，最终纳入须有可信人类确认，不凭操作名预设 human-only 分类。

### 状态与转换

分工原则：分支维度挂在既有 `attempt` 之上，不重写 `attempt` 内部状态机。候选转换：

- 固定分发基线后，宿主分发执行对话并建立分支关联；候选名 `dispatch.fanout` 不表示已有命令；
- 每分支内 attempt 沿用意图先提交、结果后结算和沙盒能力如实校验的原则，产生多方案时保留每次测试与失败依据；
- 分支产物封包为 `solution_package`，数据处理侧另外生成实现评分和审阅意见；评分不自动触发执行、选择或批准；
- 收尾准备选定包与模块整理提案，人类确认后执行显式收敛；其余包可按留存政策记为 `retained_not_selected`，未通过包也可作为过程资料留存；
- 项目正式采用与现有 `DELIVERY_READY`/交付的映射需另行设计。当前审批和交付命令不直接等同于新增模块纳入操作。

### 隔离规则改写

现有[尝试服务](../../src/project_kernel/application/attempt/service.py)允许同任务同策略在终态后复用目录，拒绝不同任务/策略的重叠目录，并保留活动或 unknown 目录占用。引入显式分支后，需要补充分支归属，候选规则为：

- **分支目录分离**：不同 `execution_branch` 的实际目录不得相同或互为祖先/后代；目录不同不意味着禁止并行运行；
- **分支内可顺序复用**：同一分支内，终态尝试可创建新 attempt；是否复用原目录仍需核对任务、策略与执行范围，不能仅凭分支 ID 放宽现有占用检查；
- 活动（running/unknown）目录继续占用，改 root current 或换对象 ID 不解除占用（沿用现有纪律）。

目录分离不代表 OS 沙盒限制。执行范围、允许读写的资源与 `required_sandbox_level` 仍需由宿主/provider 明确实施并验证，不能把 `directory_only` 描述为完整沙盒。

### “未采用也入库”的定位

这是用户要求的留存可能性，需要区分过程资料与当前正式采用：

- 留存包引用其失败、未选择或未验收状态及原因，不隐式成为项目当前选择；
- 未采用包和评分依据可用于比较、复盘或下游样本构造，但不能直接推断它是高质量训练样本；
- 保存时机、制品保留期限、容量与删除规则仍待设计；选择记录不得因候选包后来被清理而失去必要依据；
- 候选留存不改变交付状态，不能把所有候选均成功当作任务完成前提。

## 候选方案与取舍

显式 branch/package/review 对象可固定分发归属、方案版本和比较依据，代价是新增持久化对象、权限及并发验收。仅依赖既有 task/strategy/attempt 的查询聚合可复用更多现有服务，但需保证每个包与固定分发基线的关联完整，并补齐汇合与正式采用记录。查询可以组合读取已有事实，不能自行创造未持久化的分发或人类确认。最终字段与服务拆分仍未确定。

## 影响面

| 区域 | 影响 |

| `domain/flow.py` | 需明确分支、任务汇合与正式采用之间的状态关系，候选新相位不能仅从名称推定 |
| `application/attempt/service.py` | `execution_root` 校验增加分支归属，保留任务、策略、范围和历史占用检查 |

## 待决策与待验证

- 分支是否需要嵌套（分支内再 fan-out）仍待决策，本文不默认支持任何层数。
- 路线 A 已确定最终纳入由人类确认；候选命令调用主体、确认载体与失效条件需具体设计，不修改现有 `HUMAN_ONLY_COMMANDS`。
- 收敛的幂等、并发与失败回滚未设计。
- 未运行任何并行场景，本文不构成行为接受。
