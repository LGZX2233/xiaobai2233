# 智能体交换与表单实时

文档版本：1.1.0；更新日期：2026-10-12（Asia/Shanghai）。源码依据：`16410c9fbf4a8507445b4603e371e701614e4499`。归属 [K-RPC](../modules/nodes/rpc.md) 与 [K-QUERIES](../modules/nodes/queries.md)，对应 [REQ-BOUNDARY-11](../requirements/2026-10-12-kernel-boundaries.md)。状态为设计说明及静态核对，未实现 `model_exchange` 或实时表单通道；既有 `events.read` 已支持事件增量读，`release_approved=false` 不变。

## 需求原话与核心判断

用户要求：表单可**实时更新**交互；模型之间**允许交互提问**；模型更多是去看库。

本文的核心判断分两层：

> **实时性归编排层，可溯源的智能体交换归内核。**

宿主负责通道路由、实时投递、等待与取消，内核保留已提交的交互内容、依据和结果。模型主要读取项目/模块库，必要时提出问题；接收回复后仍需定位其来源与适用版本，不能把对话中的意见直接当作已确认需求或批准。

## 表单实时（归编排层）

- 前端/编排层负责表单的推送、暂态展示与编辑中状态；
- 候选持久化规则：有意提交的表单值、处理结果与验收依据成为可溯源 revision，编辑中的每次按键不必产生权威提交；现有内核尚无通用实时表单对象；
- 编排层可展示“已提交”与“暂态/编辑中”并分别标识，这与[消费者一致性](consumer-consistency.md)中“前端可展示本地编辑与 provider 暂态，但需与已提交事实分别标识”一致；
- 现有 [QueryService.events_read](../../src/project_kernel/data/queries/service.py) 已读取游标 `(commit_seq, event_index)` 之后、提交序不超过固定 `as_of_seq` 的审计事件，并按该游标顺序返回；提供 `limit` 时要求 1–1000，非法值拒绝而非钳制；
- 事件增量可提示哪些引用需要重读，不能直接等同于任意对象的字段 diff 或实时推送。模块投影、表单状态合并、断线后的刷新与缺口处理仍需设计。

任务表单候选内容包括模块基线、拆分需求、执行范围、验收标准、方案提交、待回答问题与验收结果。执行模型可提交新的实现或澄清请求，设计/收尾模型可反馈。反馈导致范围或标准变化时需形成新基线并重审受影响的测试、评分与纳入提案，不通过实时更新覆盖旧执行依据。

## 模型间交换（归内核，最小域 `model_exchange`）

候选最小域定义：

- 同一次交换使用稳定 `exchange_id` 关联问题、回复与后续状态，问题 revision 不预先引用尚不存在的回答；
- 回答 revision 引用已有的问题 revision；需要关闭或汇总时，追加新记录引用当时已有的问题与回答，保持不可变引用的提交时序；
- 每条引用**提问/回答当时读取的库帧**（水位 + 精确 ObjectRef），使“基于什么问、基于什么答”可追溯；
- 参与方标识、设计/执行/收尾角色、任务/模块/分支关联与内核提交序作为字段候选；角色字段本身不授予人类审批权限；
- 交换本身不改变任何交付/审批/执行状态，是留档事实。

与既有对象的关系：

| 对象 | 关系 |
| --- | --- |
| `requirement` | 问询需求的理解过程可落为 `model_exchange`（见[执行流映射](execution-flow-mapping.md)阶段②） |
| 实现评分与审阅 | 数据处理侧意见可以关联交换和测试依据；意见不自动成为正式 `verification` 结论或人类批准（见[模型收尾身份](model-review-identity.md)） |
| 双层存储 | 项目与模块按范围留存已提交交换；实时暂态由宿主管理，具体存储位置仍待设计（见[双层存储与收敛公理](dual-layer-storage.md)） |

## 边界规则

| 事项 | 归属 |
| --- | --- |
| 表单推送、暂态、编辑中状态 | 编排层 |
| 表单提交值成为 revision | 内核 |
| 游标后的审计事件读取 | 内核既有 `events.read` |
| 任意模块/表单的字段 diff | 只读投影候选，尚未实现 |
| 模型交换的落库与可溯源 | 内核（最小域 `model_exchange`） |
| 交换的展示、编排、路由 | 编排层 |

## 影响面

- 若采用 `model_exchange`，需新增 revision 类型、引用校验、参与方权限和读取投影；交换留存不自动推进审批、交付或执行；
- 游标事件读可复用既有 `events_read`，表单/模块差异投影需独立定义；
- 实时路由、投递与恢复属于宿主，本文未新增推送通道或后台服务。

## 候选方案与取舍

显式 `model_exchange` 可将问题、回答及读取依据固定为可查询记录，代价是需要新增数据类型与权限验收。先使用宿主日志再显式提交关联引用可减少内核改动，但必须确保模型实际收到的内容与提交内容一致，不能只留汇总而丢失改变需求的回答。两者都需处理重复投递、无回答、取消和迟到回复；实时送达不等于权威提交，权威提交也不等于对方已阅读。
