# 持续记录与学习资料

文档版本：1.3.0；更新日期：2026-10-12（Asia/Shanghai）。本文定义任务总结、项目总结、术语与错误资料、用户学习画像的文档职责；记录入口是[持续记录目录](../records/README.md)，对应模块为 [K-RECORDS](../modules/nodes/continuous-records.md)。建立要求见[持续记录需求](../requirements/2026-10-10-continuous-records.md)，适用判断、评价与阅读方法的改进见[技能成长需求](../requirements/2026-10-10-clean-layout-and-skill-growth.md)，设计讨论主动表述要求见[边界需求](../requirements/2026-10-12-kernel-boundaries.md)。

## 当前形态与权限

当前实现是仓库内 Markdown 记录和[项目维护 skill](../../.agents/skills/kernel-maintain-records/SKILL.md)。模型按任务需要读取相关文档，并在有修改授权的工作中更新记录；没有后台监听、自动实时同步、新数据库、用户画像 RPC 或新增 wire 命令。工作结束、阶段交接、决定变化和用户明确纠正信息是维护时机；尚未维护的变化不应被描述为已同步。

运行内核继续拥有项目身份、不可变业务版本、授权和证据账本。文档记录不授予权限，不替代人类审批，不把静态判断转成运行结果，也不进入冻结 G2 的独立裁决。用户学习画像采用可纠正的文字描述，不产生评分、排名或权限。

## 一项事实只有一个主记录

| 记录 | 主职责 | 事实来源与引用规则 |
| --- | --- | --- |
| [任务总结](../records/tasks/2026-10-10-kernel-maintenance.md) | 本次目标、范围、选择、产物、已知问题和交接事项 | 引用需求 ID、模块 ID、源代码版本、实际执行记录和问题主文档；未执行的动作写明未执行 |
| [项目总结](../records/project-summary.md) | 当前项目目标、能力位置和下一步 | 索引架构、当前状态、任务记录和历史接受依据；详细验收事实仍由原验收记录拥有 |
| [术语与错误资料](../records/terms-and-errors.md) | 项目术语、错误条件、影响和理解资料 | 问题严重度、修复与验证状态引用设计审查或后续修复记录；不虚构新的运行失败 |
| [用户学习画像](../records/user-learning-profile.md) | 已确认的沟通偏好、学习需要和知识熟悉程度 | 用户明确表述为已确认事实；未确认推断单独标记，默认不进入当前画像 |
| [学习资料](../records/learning/2026-10-10-modules-and-rules.md) | 有项目实例的概念解释 | 引用术语资料和模块主文档；示例不是用户能力结论，也不是产品能力验收 |

需求状态以需求记录为主，节点关系以[模块目录](../modules/README.md)为主，接受状态以相应验收记录为主。摘要可以写必要结论并附链接，不手抄所有条件、JUnit 项目或证据清单。记录文件不是运行内核的业务 revision。

## 元数据与精确来源

每份记录包含稳定 `record_id`、`record_version`、`updated_at`、`timezone`、`source_revision`、`source_worktree`、`status`、`requirement_ids`、`module_ids` 和 `acceptance_status`。记录版本递增代表该记录完成了一次维护，与内核版本、Schema 版本和业务 revision 各自独立；更新时间只精确到实际可确认的粒度，不补造时分秒。

源码结论的 `source_revision` 写完整 Git 提交；若依据包含未提交工作，`source_worktree` 明确写出范围。单个结论依赖另一个版本时，在该条旁注明，不用文件顶部的源码版本替代所有来源。用户表述写实际日期和“用户明确要求”，不猜测对话 ID、个人信息或知识水平；本轮没有建立对话节点关联。

所有记录保留“已接受”“静态发现”“未验证”“未实施”的区别。历史 G2 的25项87条件只能引用原结果；本轮新资料的文档交付和运行能力接受分别记录，没有新行为接受时写 `not_behaviorally_validated`。

## 维护步骤

1. 先读目标节点、关联需求、当前记录和它们引用的主文档，确认本次要更新的事实范围。
2. 记录实际动作、输入版本和可用结果；把静态发现、推断、用户偏好和运行事实分别表述。没有证据时写未知或未执行。
3. 更新事实主文档，再更新必要的摘要、学习资料和链接；对尚未到达交付阶段的任务保留进行中状态。
4. 用户纠正知识程度、偏好或学习需求时，立即替换当前有效描述并保留简短修订原因；不从单次提问或一次错误推断长期能力。
5. 增加记录版本、实际更新日期和一条修订记录，核对需求、节点和主记录链接。验证范围遵从本次授权；用户已要求不测试时，不把维护步骤解释成测试授权。

## 修订、撤回与删除

正常修订更新当前记录，并在版本历史中标明哪些事实被纠正及其依据。替代记录使用原稳定 ID 或明确 `supersedes` 指向，不让两个“当前”文档同时拥有同一事实。

撤回的结论标记为撤回或失效，并从当前摘要和上下文推荐中移除；如果需要保留决策历史，保留撤回理由和替代链接即可。来源撤回不自动改写冻结验收或业务账本，涉及这些资料时另循其维护规则。

用户要求删除学习画像或个人偏好时，删除当前画像中的相应内容及维护者控制的派生副本，不在修订理由中重新抄写被删除内容。Git 已提交历史不等同于工作树删除；本流程不声称能清除所有历史副本，不擅自改写 Git 历史或冻结证据。删除可留不含原内容的日期和范围记录。

## Skill 与上下文读取

维护 [kernel-maintain-records skill](../../.agents/skills/kernel-maintain-records/SKILL.md) 保存可复用的读取、判断和更新步骤，记录目录保存项目事实与用户描述。任务总结不会自动变成 skill，用户画像也不是执行指令；模型采用画像调整解释深度时，当前用户要求仍优先。

是否使用 skill 由任务与[当前版本范围](../records/skills/registry.json)决定；[成长方法](skill-growth.md)拥有复用评价、反例、修订与待验证状态。技能可以按实际证据评价，用户信息和知识画像仍不评分。读者入口、学习解释和审计记录有不同目的，按具体目的组织内容，元数据不要求每篇正文都采用交接清单。当前指引由 Codex agent 使用，未装配到内核运行服务。

按节点获取上下文时，先读取节点主文档与当前需求，再选必要的任务记录、主记录和一层相关节点。只有相关性明确时才读用户画像、历史验收或错误材料；摘要中保留来源版本和未验证状态。资料不足时回到来源，不用摘要补造实现细节。

运行集成属于独立后续工作：若宿主需要自动触发维护、记录消费事件或把材料输入模型，需另行定义授权、隔离、修订、撤回、失败处理及可重建的来源记录。当前文档和 skill 不构成这些运行能力已经实现或接受的证据。

## 设计讨论的主动表述

本要求最初由用户于 2026-10-12 同一会话提出，现固化为常设工作要求（[REQ-BOUNDARY-12](../requirements/2026-10-12-kernel-boundaries.md)）：**设计部分应主动讨论技术方案与细节**，不等待用户逐条补全。

要求包含三点，均可核对：

1. 对未定的设计点主动给出**候选方案**，而非只复述用户输入；
2. 每个候选方案给出**取舍理由**与**影响面**（改动哪些区域、成本量级）；
3. 遇到与既有纪律冲突时，先指出冲突并核对已有授权；只有尚未决定且不能独立推进的事项才请用户选择，不代为默认放开限制，也不对已选路线反复询问。

记录形态要求：设计讨论的记录中应能见到“候选方案 + 取舍 + 影响”三段结构；只有复述而没有候选/取舍的段落视为未满足本条。主动讨论不改变四条基本纪律：不把设计意图读成已实现、不伪造行为接受、不越过用户授权改运行代码、不修改冻结证据与签字。相关落点见[任务记录](../records/tasks/2026-10-12-kernel-boundaries.md)追加轮。

用户在 2026-10-12 明确要求“实施时多分发代理执行”。实施按可独立复核的职责与文件分工，列明每个代理的输入、修改范围和预期交付，避免多人同时修改同一文件。主代理汇总决策、检查跨模块引用与同一事实的措辞，并报告实际执行的验证。多代理不扩大运行或外部操作授权；本次文档校准的实际分工见同轮任务记录。
