# 执行流八阶段与内核能力映射

文档版本：1.1.0；更新日期：2026-10-12（Asia/Shanghai）。源码依据：`16410c9fbf4a8507445b4603e371e701614e4499`。归属 [K-EXECUTION](../modules/nodes/execution.md) 与 [K-DELIVERY](../modules/nodes/delivery.md)，对应 [REQ-BOUNDARY-06](../requirements/2026-10-12-kernel-boundaries.md)。状态为设计说明及静态核对，新增结构未实现、未行为验证，`release_approved=false` 不变。

## 完整执行流与分工

用户给出的流程是：设计模型阅读项目整体架构与需求 → 询问并理解需求 → 拆分需求，给出各执行范围和验收标准 → 分发并行执行对话 → 执行模型在沙盒尝试不同实现 → 通过任务表单通讯及提交模块方案包 → 收尾模型评分审阅、整理模块和处理耦合 → 并入主库。

项目整体与模块独立分别拥有版本化架构和需求，模块材料供执行流阅读；两套视图需保留对应版本和关联，不能把模块执行范围从项目约束中分离。物理分库只是存储候选，不是用户这项分工的必然要求。执行模型可以提交多种实现，在测试结果之外附各实现评分并打包；未采用包可以保留，留存不等于主库采用。模型间可以提问、表单可以实时更新，但模型还需读取库中的固定依据，而不能只靠对话传递状态。

收尾身份已经选择[路线 A](model-review-identity.md)：模型评分、审阅和准备入库；人类确认最终入库；模型或编排执行已授权动作。skill 四维评分接口仍仅供数据处理，不进入执行流或审批。

## 逐段映射

“已有”指相关现有机制与该动作匹配；“部分”指已有基础但未覆盖所需粒度或宿主流程；“缺失”指没有对应的新结构。下表依据定向静态阅读，不表示真实宿主接受。

| 阶段 | 内核现状 | 判断 | 依据与差距 |
| --- | --- | --- | --- |
| ① 设计模型看整体架构 | 项目查询、模块文档树及独立 `ContextResolver` | 部分 | 文档和事实可读；knowledge 未接 RPC，项目/模块架构与实际模型请求的固定关联尚待实现，见[消费者一致性](consumer-consistency.md)。 |
| ② 问询、拆需求与执行范围 | `requirement.save`/`requirement.confirm`、design 与派发 packet 固定引用 | 部分 | 最终需求、验收项与范围有载体；问询过程、模块拆分和每分支依据还需记录关联。 |
| ③ 分发并行执行对话 | 多 attempt、策略、独立 execution_root；`EXECUTING` 允许继续 `attempt.start` | 部分 | 独立目录的多次尝试未被全局禁止；无分发批次、分支归属、子对话及聚合收敛对象，也无宿主并行调度接受。 |
| ④ 执行在沙盒处理 | 独立目录、provider 沙盒能力声明和最低级别校验 | 部分 | 目录隔离已实现；当前实际保证为 `directory_only`，不是 OS 沙盒。真实隔离及并行执行由宿主/provider 验证。 |
| ⑤ 提交多种模块方案包及评分 | 策略、attempt 比较查询、制品摘要与归档能力 | 部分 | 有结果和制品基础；方案包对象、包级验收/评分版本及不采用包的明确留存方式尚未实现。 |
| ⑥ 任务表单通讯验收 | verification、AcceptanceItem、可信人审及审批 | 部分 | 固定候选的验收链路存在；实时表单、多执行对话通信及模块粒度绑定不等于现有 verification。 |
| ⑦ 收尾模型评分、审阅和整理模块 | 查询、验收及人工批准提供依据；模型方案评分和耦合报告未实现 | 部分 | 采用路线 A；模型产出意见，人工确认入库。知识 `ScoreEngine` 和人类 `verification.record_review` 均不能当作机器方案评分接口。 |
| ⑧ 并入主库并确认效果 | delivery、task.close、归档与现有批准生命周期 | 部分 | 新模块收敛和主库目标未实现，SCM provider 未接入；已批准不等于已并入，须记录实际效果。 |

模型交换与实时表单的分工见[智能体交换与表单实时](agent-exchange-and-live-forms.md)；项目/模块存储分工见[双层存储](dual-layer-storage.md)；不同目标的完成含义见[SCM 效果映射](scm-effect-mapping.md)。

## 并行需要哪些新增语义

[task 状态规则](../../src/project_kernel/domain/flow.py) 允许 `EXECUTING` 中再次 `attempt.start`；[attempt 服务](../../src/project_kernel/application/attempt/service.py) 根据目录是否相同或互为祖先/后代判断重叠。不同任务或策略不得重叠，活动或 unknown 尝试不能复用重叠目录；独立目录不受这两项重叠拒绝限制。因此“当前只能单分支顺序重试”不是源码能支持的结论，也不能反向宣称完整并行工作流已实现。

用户需要的新增语义是：一次分发绑定多个执行对话、每分支的需求/架构/范围/验收版本、分支内多个方案包，以及跨分支的比较、人工确认和模块收敛。只有执行次数和查询比较无法表达这些关联。候选结构见[并行分支与方案包](parallel-branches.md)；该方案需复用现有 attempt 事实和占用纪律，不能因加入分支名而解除活动目录占用。

## 候选方案、取舍与影响

| 方案 | 取舍 | 影响面 |
| --- | --- | --- |
| 宿主先编排多个现有 attempt、对话和查询 | 可利用现有基础，但批次/分支/包级关联需由宿主明确记录；不能把临时查询当成已确定的收敛 | 宿主上下文、调度、表单及来源记录 |
| 增加显式分支、方案包与收敛记录 | 可以固定聚合依据和版本；需要设计并发、授权、幂等、失败和包级验收 | domain、attempt/delivery 应用、数据记录、查询及 provider 接入 |

这是设计候选，不要求内核承担模型调度、表单推送或后台对账。方案评分与耦合度量可作为数据处理结果供收尾阅读；它们不自动授予审批或触发执行。模块整理、低耦合与职责集中建议见[耦合度量](coupling-metric-boundary.md)。
