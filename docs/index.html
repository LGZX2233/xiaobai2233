科研 Agent 与 Harness 工程 · AGH 插件

科研 agent 跑得越久，
越不可信。

01

注意力会丢

对话越长，早期事实越容易被忽略。第 40 轮时，那次没通过验收的网格搜索可能已被忘掉。

02

记忆会断

关掉会话，"试过什么、结果如何、为什么选它"归零，只能重跑或重读聊天记录。

03

错误会重复

卡死的求解器被当成"没跑"再启动；超时的写入被再写一次，外部效果被翻倍。

04

过程是黑箱

模型说"α=0.9，已验证"，没人能核对；谁批准了什么，没有记录。

05

记录是散的

每个对话各记各的。回头看项目结构、技术债、模型哪里理解错了，只能翻聊天记录。

更大的模型能缓解一部分，但"事实放在哪里、由谁裁决"不是模型能力问题。我们绕开模型的局限，不声称修好它，也不碰 Transformer。

做法：把记忆和过程搬出上下文，存进一份只追加的账本。模型调用工具去查，结果由独立程序重算，交付由人从模型够不到的入口放行。内核不规划，只记录、校验、拦截。

  • accepted_g2 · release_approved=false
  • 证据模式 test
  • 隔离 directory_only（非 OS 沙盒）
  • 演示数据为合成数据
  • 自有 JSON-RPC，非 MCP
  • 仅在 AGH 上验证

一次运行 · 一维热传导反问题

账本里的一次真实反演

反演热扩散系数 α：真值 0.37，固定种子合成数据，相对容差 5%。三种策略，一个卡死，一个失败，一个通过。每一行对应内核里的一次提交；顺序和数值取自 tests/p14_science_demo 与 adapters/agh-plugin/test/tools.test.mjs。

#调用内核记录了什么状态
01pk_state模型先读账本：任务、策略 s1/s2/s3、环境检查，以及推荐步骤 guide（里面写着"你不能批准"）。read
02pk_run_strategy s3求解器卡死，轮询超时。结算为 unknown 并保留；查询、比较、同键重放都不再启动它。? unknown
03pk_run_strategy s1网格搜索（步长 0.05）完成，拟合 α=0.35000。completed
04pk_verify s1checker 用闭式解对 9 个读数取中位数重算，得 0.3786；0.3500 与它相差 7.55%，超出 5%。失败被记录，不删除。× fail
05pk_run_strategy s2黄金分割 30 次迭代完成，拟合 α=0.37286。completed
06pk_verify s2独立重算通过：与闭式参考相差 1.51%，距真值 0.77%；读数与固定种子数据逐项一致（≤1e-12）。✓ pass
07pk_compare三个尝试并列；failures_retained 含 s3；缺失的用量记为未知，不是 0。compared
08pk_select s2模型写下选择理由，连同比较对象一起存档。selected
09pk_request_delivery冻结交付快照，生成 pending 审批，绑定 snapshot_digest。模型到此停下。◆ pending
10人 · 终端tools\pk-human-approve.ps1：人核对摘要，亲手输入前 8 位。机器通道发同一命令，返回 UNSUPPORTED_COMMAND。◆ approved
11pk_apply_delivery交付执行；之后的 reconcile 只观察，不重放写入。✓ applied
12pk_events按提交序号核对整条链的事件。read

上表是推荐顺序，也是测试走的顺序。真实模型的顺序由它自己决定：evidence/rehearsal/ 里的预演（AGH 之外，DeepSeek 与 Agnes 各两次）中，模型都是先跑完三个策略，再逐个校验。

设计

四个支柱，每一项都有代码位置

01

记忆与记录

事实在账本里，不在上下文里。

  • 不可变账本：revision、事件、回执同事务提交data/store/uow.py
  • 读水位：回看任意提交序号，落后如实标注data/queries/watermarks.py
  • unknown 保留不重跑science_executor.py · application/attempt/service.py
  • 幂等回执：同键重放返回原回执data/store/uow.py
  • 失败不删，缺失不当零data/queries/service.py
  • 备份与恢复 （生产恢复未启用）evidence/backup.py
02

信任与治理

模型说了不算。

  • 独立复算：闭式解，不信自报tests/p14_science_demo/science_checker.py
  • 人工专属命令：机器通道得 UNSUPPORTED_COMMANDinterfaces/rpc/policy.py
  • 快照绑定审批，候选变化后旧批准作废application/delivery/service.py
  • 规则只能收紧：只有 deny，allow 被拒application/design/service.py
  • 只观察的对账domain/delivery/effect.py
  • 终端人工确认 （交互证明，不是安全边界）tools/pk_human_approve.py
  • 目录隔离 （directory_only，不是 OS 沙盒）science_executor.py
03

结构与可视

给人审阅结构和技术债。

  • 23 节点模块树：单根、无环docs/modules/registry.json
  • 只读查询：追溯、覆盖、时间线、环境data/queries/
  • 14 视图面板：总览 设计 工作区 结构 需求 执行 审批 环境 版本 事件 错误 文档 Skill 知识adapters/agh-plugin/client/src/views/
  • 来源分四类标注：实时 / 文档声明 / 派生 / 设计预览
  • 设计视图：痛点 → 机制 → 位置 → 状态
04

集成

挂在宿主旁边，不接管规划。

执行闭环

AGH 与模型怎样驱动它

AGENT 运行时

Agnes Harness

  • 加载插件，把 pk_* 工具交给模型
  • 执行工具调用，把结果送回模型
  • 渲染 Project Kernel 面板
  • 规划、能力调用、反馈处理三步都在这里
规划者

AGH 里的模型

  • DeepSeek（队长选定）。API 报告的 id：deepseek-flash、deepseek-v4-pro；版本标签"DeepSeek V4.1 Flash" API 未确认，待队长确认
  • Agnes 3.0 Flash（agnes-3.0-flash，provider agnes-ai）：已用 API 验证能返回工具调用，AGH 之外的预演有 2 次记录；是否出现在 AGH 运行记录里，以 evidence/agh-run/ 为准
  • OpenAI 兼容 chat completions + tool calling
记录 · 校验 · 拦截

Project Kernel

  • 不规划，不替模型决定下一步
  • 插件里没有审批工具
  • 人工批准走独立终端入口
  • 内核本身不调用任何模型
第一道门：AGH 的工具权限确认。模型要调用 pk_request_delivery 时，AGH 先请人确认这次工具调用（沙盒观察到约 60 秒不处理会超时，模型会如实报告"没有执行"）。
第二道门：内核的人工审批。交付请求产生 pending 审批后，必须由人在终端输入快照摘要前 8 位；这是交互确认，不是安全边界。

工具：pk_state · pk_run_strategy · pk_verify · pk_compare · pk_select · pk_request_delivery · pk_apply_delivery · pk_events。密钥只在 AGH 设置页填写，不进任何文件。AGH 之外已有 4 次预演（deepseek-flash 与 agnes-3.0-flash 各 2 次），经聊天补全 API 驱动同一组工具和同一个内核，每次 9 次接口调用、总 token 约 2.9 万至 3.1 万，都选 s2、α=0.37286、交付 applied（evidence/rehearsal/summary.md）；其中人工批准一步由操作员脚本完成，不是模型。预演不是 AGH 运行。

验证与异常处理

三类测试样例

正常

  • s2 黄金分割通过
  • s1 粗网格没达到容差
  • 选择 s2 并写理由
  • 人工批准后交付 applied

边界

  • 伪造 α=0.9 被拒
  • 机器通道批准：UNSUPPORTED_COMMAND
  • 批准后候选变化：旧批准 superseded
  • allow 规则：INVALID_INPUT
  • 跨项目查询：SCOPE_MISMATCH

失败

  • s3 卡死：unknown 保留，启动次数不变
  • 同键重放返回原回执
  • reconcile 不重放写入
  • 关库重启，水位读取结果不变
