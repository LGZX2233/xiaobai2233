## 2. 工具调用链

模型在 AGH 中按下列顺序调用。具体顺序由模型决定，内核只记录与校验；下面是推荐顺序，也是 `tools.test.mjs` 里测试走的顺序：

```
pk_state                 读取任务、策略 s1/s2/s3、环境、guide、已有进度
pk_run_strategy(s3)      → attempt.start → 轮询超时 → unknown（保留，不重跑）
pk_run_strategy(s1)      → attempt.start → completed
pk_verify(s1)            → host.publish_candidate + verification.run → passed=false（alpha_fit 0.35）
pk_run_strategy(s2)      → attempt.start → completed
pk_verify(s2)            → verification.run → passed=true（alpha_fit 0.37286）
pk_compare               → attempts.compare（三个 attempt 并列，failures_retained 含 s3）
pk_select(s2, reason)    → attempt.select（保存比较对象与理由）
pk_request_delivery      → delivery.request → 冻结快照，pending 审批（含 snapshot_digest）
人工批准                 → tools\pk-human-approve.ps1 → 独立 human 入口 approval.decide（不经 AGH、不经模型）
pk_apply_delivery        → delivery.apply → applied
pk_events                → events.read（核对整条链的提交事件）
```

可由代码核对的事实（均已读过源码或测试）：

- 8 个工具定义在 `adapters/agh-plugin/index.mjs` 的 `createTools`：`pk_state`、`pk_run_strategy`、`pk_verify`、`pk_compare`、`pk_select`、`pk_request_delivery`、`pk_apply_delivery`、`pk_events`。插件版本 0.3.1（`adapters/agh-plugin/package.json`）。
- 工具参数是短 id：`pk_run_strategy {strategy_id}`、`pk_verify {strategy_id}`、`pk_select {strategy_id, reason}`、`pk_request_delivery {}`、`pk_apply_delivery {}`。对象引用由插件按会话记住。
- 插件里没有审批工具；`tools.test.mjs` 第 39 行断言工具名里不含 `approve` 或 `decide`。机器通道调用 `approval.decide` 返回 `UNSUPPORTED_COMMAND`（`test_heat_inversion_flow.py` 第 103–108 行）。
- `pk_state` 返回的 `guide` 字段（`index.mjs` 的 `WORKFLOW_GUIDE`）给模型列出推荐步骤，并写明"你不能批准"。是否照做由模型决定，内核只拦截。
- `pk_request_delivery` 的工具元数据是 `requiresApproval: "always"`。这是 **AGH 自己的工具权限提示**（AGH 在执行该工具前向用户确认），和内核里"绑定快照摘要的人工审批"是两回事，不要混为一谈。AGH 弹窗的实际样子以 `evidence/agh-run/` 里的截图为准。
- 实机观察（探索性运行，非最终证据）：在 AGH 网页里，模型调用 `pk_request_delivery` 时 AGH 弹出自己的工具权限确认框；无人处理约 60 秒后超时，模型在回复里如实说明交付请求超时、动作没有执行，并请用户确认后再调用（截图见 `outputs/agh-run/explore/06-approval-*.png`、`07-end.png`，归档后以 `evidence/agh-run/` 为准）。同一次运行里，s1、s2、s3 三个 attempt 都被保留，没有重跑，模型是 `deepseek-flash`（界面底部的模型选择器与消息时间戳旁可见）。这说明录制时必须有人点掉这个框，否则演示卡在这里。
- AGH 实机探索截图（在 `outputs/agh-run/screens/`，尚未归档到 `evidence/agh-run/`，模型为 `deepseek-flash`）：`10-agh-approval-dialog-light.png` 是总览视图，s3「未知·不重跑」、s1「失败·保留」、s2「通过·已选定」并列，对话区里 AGH 弹出 `pk_request_delivery` 的确认框，会话状态"等待审批"；`09-agh-panel-open-light.png` 是总览，此时还没有尝试。`11-panel-permissions-pending-light.png` 与 `12-panel-permissions-approved-light.png` 的文件名写着 pending / approved，但实际画面是审批队列为空、会话已完成、模型报告交付请求超时，**不能当作"pending"或"已批准"的证据**。所以截至撰写时，**没有"AGH 内人工批准成功并 applied"的截图或记录**；若不补录，视频和材料里不得声称 AGH 内完成了交付。
- 未批准时 `pk_apply_delivery` 返回 `applied: false`、内核错误码 `APPROVAL_INVALID` 和去终端批准的提示（`tools.test.mjs` 第 74–77 行）。
- 人工批准程序 `tools/pk_human_approve.py`（经 `tools\pk-human-approve.ps1`）要求人亲手输入快照摘要前 8 位。它是交互确认，**不是安全边界**：能登录这台机器的人也能运行它（文件头注释同样写明）。

### 2.1 已有的一次预演里实际发生了什么（读自 `summary.md` 与 jsonl）

这是 AGH 之外的预演，不是 AGH 运行。

- 工具顺序（模型自己的选择）：`pk_state → pk_run_strategy(s1) → pk_run_strategy(s2) → pk_run_strategy(s3) → pk_verify(s1) → pk_verify(s2) → pk_compare → pk_select(s2) → pk_request_delivery → pk_apply_delivery`。
- 结果：s3 `unknown`；s1 校验未通过；s2 校验通过；选 s2；审批 `pending`；批准后 `apply.applied` 为真，操作状态 `applied`，最终 alpha 0.3728610547894271；没有"提前 apply"。
- 模型写的选择理由（原文）："s2（黄金分割）alpha≈0.37286，与闭式解 0.3786 相对偏差约1.5%，在5%容差内，独立校验通过；s1 校验失败、s3 卡住。"
- 人工批准一步由**操作员脚本**调用 `tools/pk_human_approve.py` 的 `decide()` 完成（摘要前缀由脚本输入），jsonl 里记为 `human step performed by operator script in rehearsal`；模型本身没有批准能力。
- 这份记录**不能证明**"模型因 s1 失败而改变策略"：提示词要求"把可用的策略都跑一遍并逐个校验"，模型先跑完 s1、s2、s3 再校验。它证明的是：模型能用同一组短参数工具走完整条链，并在 pending 处停下。
