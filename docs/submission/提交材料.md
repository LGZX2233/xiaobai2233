## 一、项目说明

**项目名称**：Project Kernel：给 AGH 的外置项目账本

**参赛组别**：{{参赛组别}}（交接文档写的是本科组）　**学校与专业**：{{学校}} / {{专业}}　**参考方向**：科研 Agent 与 Harness 工程

**项目摘要**：
LLM agent 做长流程科研任务时，长上下文里的注意力会衰减，跨会话后"试过什么、为什么选它"会丢，卡死或超时的任务会被当成没跑而重来，整个过程对人是黑箱，记录还散落在各个对话里。Project Kernel 把记忆和过程从模型上下文里搬出来，存成一份只追加、可按时间点回查的结构化账本，以 AGH 插件的形式交给模型调用。模型负责规划和选工具；内核只记录、校验、拦截；结果由独立 checker 重算；交付必须由人从模型够不到的入口批准，批准绑定快照摘要。演示任务是一维热传导反问题（反演热扩散系数 α，真值 0.37，容差 5%，合成数据）：卡死的 s3 记为 unknown 且不重跑；粗网格 s1 得 α=0.3500，被判失败并保留；黄金分割 s2 得 α=0.37286，通过独立闭式重算；把 α 伪造成 0.9 被拒；机器通道自己批准返回 `UNSUPPORTED_COMMAND`。我们绕开模型的局限，不声称修好了模型。

**问题来源**：
我们用 agent 跑多步骤科研流程时反复遇到的问题：执行记录不清晰（黑箱）；多模型、大项目难以协作；模型不了解环境、重复造轮子；需求不清、不知道用户的知识和能力边界；程序结构混乱；不会探索和比较方案；长对话里注意力丢失、成本上升；过程数据没有留存，无法回看结构和技术债；缺少审批和隔离这类公司化治理；每个对话各记各的，耦合高；记录无法在不同 agent 框架间互通；人和模型的沟通随意、没有标准表单。其中前几项在本项目里有对应机制和测试，后几项只有设计，具体对应关系见 [README 的痛点表](../../README.md)，每一行都标了状态。

**项目目标**：让 agent 的每一次尝试、失败、未知、选择理由、审批和交付都成为可查询、可追溯的一等记录；让模型自报的结果必须经独立复算才算数；让交付必须经人批准；让人能在 AGH 面板里回看结构和过程。

**核心方法**：
- 记忆与记录：revision、head 历史、事件、审计、命令回执在同一个 UnitOfWork 里提交；`as_of_seq` 读水位可回看历史，重启不丢；失败和未知不删除；幂等键重放返回原回执。
- 信任与治理：独立 checker 用闭式解重算；审批命令只在人工入口，机器通道返回 `UNSUPPORTED_COMMAND`；批准绑定快照摘要，候选变化后旧批准作废；规则只能收紧（`deny`），不允许 `allow`；`unknown` 不自动重跑；`reconcile` 只观察、不重放写入。
- 结构与可视：23 节点模块树、追溯、覆盖、时间线、环境报告，在 AGH 面板里展示（13 个只读服务，面板导航 14 项）。
- 集成：版本化 stdio JSON-RPC + 冻结 JSON Schema（`contracts/v1`），作为 AGH 插件运行，不改 AGH 源码。这是自有协议，不是 MCP；只在 AGH 上验证过。

**Agnes Harness 执行流程**：
AGH 加载插件 `@project-kernel/agh-plugin`，把 `pk_*` 工具交给模型。模型依次决定并调用：`pk_state`（读任务与策略）→ `pk_run_strategy`（跑 s1/s2/s3）→ `pk_verify`（独立校验，失败结果照样保留）→ `pk_compare` → `pk_select`（写理由）→ `pk_request_delivery`（产生 pending 审批，模型停下）→ 人在终端运行 `tools\pk-human-approve.ps1` 批准 → 用户告诉模型"已批准，请执行交付" → `pk_apply_delivery` → `pk_events`（核对记录）。调用顺序由模型决定；内核没有规划类工具或服务。

**所用模型的名称与版本**：

| 用途 | 模型 | 说明 | 证据 |
| --- | --- | --- | --- |
| AGH 运行（队长选定） | DeepSeek；API `/models` 报告的 id 为 `deepseek-flash`、`deepseek-v4-pro`；实际运行所用 id：`deepseek-flash`（AGH 导出与 cost/ledger 记录一致） | 用户使用的版本标签"DeepSeek V4.1 Flash" API 未确认，**待队长确认** | AGH 实机：主运行 `evidence/agh-run/20261015-1011-deepseek-flash/`（9 次工具调用，见 [运行证据](运行证据.md)）。AGH 之外的预演：`evidence/rehearsal/`，id `deepseek-flash` |
| 赛方要求的 Agnes 模型 | Agnes 3.0 Flash，id `agnes-3.0-flash`，AGH 内 provider `agnes-ai`，网关 `https://api.agnes-ai.cn/v1` | 已通过 API 验证能返回工具调用；AGH 之外的预演（`evidence/rehearsal/`）有 2 次 `agnes-3.0-flash` 记录，均走完整条链并 `applied`，但那不是 AGH 运行。另有一次在官方 AGH 内的完整运行：`evidence/agh-run/20261015-0921-agnes-3.0-flash/`（记录里模型只有 `agnes-3.0-flash`），作为补充运行 | provider 定义在 AGH 源码 `packages/ai/src/adapters/pi/providers/agnes-ai.ts` |

模型 id 和 provider 名取自 AGH 源码与 API 返回，不是凭印象写的。

**使用环节**：模型只在 AGH 的任务循环里使用：读账本、决定跑哪些策略与顺序、读独立校验的结果（含失败）、选择通过的策略并写理由、发起交付、人批准后执行交付、核对事件。内核支持"某个策略失败后改跑别的策略"，但现有预演记录里模型是先把三个策略都跑完再校验（提示词要求如此），因此记录不能证明"因失败而换策略"；AGH 实机记录里是否出现，以 `evidence/agh-run/` 为准。内核本身不调用模型（`src/project_kernel/ports/ports.py` 里的 `ModelPort` 只是端口，`adapters/agnes-model/` 里的实现有单测，未接入 AGH 运行）。

**调用方式**：AGH 内置 provider，OpenAI 兼容 chat completions + tool calling。账号和密钥只由用户在 AGH 设置页填写，不写入任何文件、命令或文档。

**验证方法**：
- 自动测试：`tests/p14_science_demo` 与 `tests/p15_innovation_showcase`（7 项）覆盖正常、边界、失败三类样例；全量 `tests` 627 项；插件 node 测试（工具、服务、轮询）16 项。
- 独立复算：`tests/p14_science_demo/science_checker.py` 不信求解器自报的数字，用闭式解对 9 个读数取中位数重算，并核对读数与固定种子数据集逐项一致（误差 ≤1e-12）。
- 实机记录：官方 AGH 构建（Linux 沙盒，自动化浏览器驱动）内的真实模型运行，会话导出、工具调用链、账本事件、人工审批终端记录见 `evidence/agh-run/20261015-1011-deepseek-flash/`；录屏即演示视频。
- 状态口径：内核历史状态 `accepted_g2`，`release_approved=false`；证据模式 `test`；执行隔离 `directory_only`（不是操作系统沙盒）。

## 六、基本信息与技术信息（早期通知中的字段）
