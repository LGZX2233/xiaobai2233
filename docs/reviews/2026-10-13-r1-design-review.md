# R1 复现规格设计评价

文档版本：1.0.0；日期：2026-10-13（Asia/Shanghai）。评价对象：[从零复现总指南](../reproduction-blueprint.md) 及四章规格（`reproduction/01`–`04`）。本评价是设计评审意见，不改变 R1 规格的任何字段与状态；`release_approved=false` 不变。

## 1. 总体结论

成色高于常见"参考实现规格"：12 条不变式、12 故障点恢复矩阵、33 项验收条件构成可机械验证的负向行为矩阵；六层"完成"分层（回执→持久化→候选验收→人审→外部效果→采用发布）是全文最有价值的架构决策，直接消灭"外部 commit 成功 = 项目已采用"这类事故来源。

主要风险不在设计错误，而在**宿主/内核边界的两处渗透**（host_work 表、表单暂态留白）与**三套评分机制"纪律防混"而非"结构防混"**。实施前需钉死第 3 节所列事项。

## 2. 各章评价

| 章 | 评价 | 实施前必须处理 |
| --- | --- | --- |
| 01 数据与事务 | 最强。不可变 revision、CAS、幂等双查、两阶段制品与 v1 `UnitOfWork`/`ArtifactStorage` 同构，S0–S1 可直接平移复用 | `host_work` 归属（见 §3.1）；不可变表触发器白名单与可变协调列的边界 |

| 04 实施与验收 | S0–S7 切片顺序合理，33 项 R1-AC 全部 not_run，负向验收完整 | 缺"模块多分支并发写时项目查询锁等待/增长后行为"验收项（§3.6） |

## 3. 实施前必须钉死的事项

1. **host_work 越权。** 01 章把宿主持久队列写进内核 DDL，等于内核持有一份宿主调度状态：宿主领取/续租/结算拿 SQLite 写锁（与业务 UoW 争锁热点）；它可变又住在有不可变触发器的库里，可变列白名单未定义；宿主与内核两份状态需对账，规格无对账规则，且违反 02 章"业务结论只能从 attempt/report/operation 与审计读取"的纪律。建议：host_work 移出内核 DDL，宿主用自有持久队列；内核只保留不可变的意图/观察 audit 事件（03 章 model_call 事件族已正确），宿主与内核以"精确引用 + operation_key"对齐。
2. **表单暂态留白。** 规格只定义了提交侧（current 已提交快照、并发 CAS 冲突返回双方引用），未定义暂态侧：按键暂态过期规则、宿主崩溃恢复、多宿主同表单编辑。"表单实时更新交互"是用户明确需求，暂态规则不定义则实施模型各造一套。
3. **model_exchange 唤醒机制。** question 提交后谁、在什么触发下读并投递给设计模型，规格只有"宿主实时通道"一句；不定义则问答退化为轮询异步留言。
4. **评分三套结构防混。** 方案评价 / knowledge ScoreEngine / skill 四维目前靠散文纪律区分；建议把"skill/knowledge 记录不可被 implementation_review 或路由消费"下沉到 schema 层（review 的 evaluator 只接受 ModelSpec）。
5. **exact 计量路径。** 多数 provider 无法提供确定 tokenizer 容量，生产上实际只有 estimated+margin，超窗靠 provider 拒绝后调材料。建议在 provider capability 声明中写明 input_limit 来源与计量模式可用性，避免实施模型误以为 exact 是可靠默认。
6. **并发增长验收。** R1-AC 矩阵补 1–2 项：模块多分支并发写时项目查询锁等待、数据增长后类型索引路径 vs 全表扫描退化。

## 4. 与用户执行流的对应关系核对

用户要求（设计看整体/问需求/拆范围验收 → 分发并行 → 沙盒多方案包 → 表单通讯 + 模型问答 → 收尾评分审阅并入主库；项目/模块两套架构需求，模块部分给执行流；保留数据拼上下文、留档、训练、用户知识、skill；引入公司代码管理）与 R1 八阶段逐段可对应。已确认设计覆盖：分发批次、多 attempt 多包、保留未采用包（retention_state）、路线 A 人审、SCM 目标（effect_kind/条件更新/tree 映射）。欠规格点集中在 §3.1–3.3（交互子系统）与 §3.5（计量现实性）。

## 5. 结论与建议顺序

1. 按 §3.1 处置 host_work（决策：移出内核 DDL 或给出可变列白名单 + 对账规则），更新 01/02 章。
2. 补表单暂态与问答唤醒规格（02 章第 10 节扩展）。
3. 计量模式与 provider capability 声明字段对齐（03 章第 3 节）。
4. 评审通过后，按 04 章 S0→S7 分发实施；R1 验收执行前规格内 33 项保持 not_run。
