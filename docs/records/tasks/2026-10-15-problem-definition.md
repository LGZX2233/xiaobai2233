# 问题定义修订记录

## 目的

按用户补充的 12 类失效重新组织 README 的问题定义，使提交材料先说明真实痛点、失败后果和需要补齐的项目事实，再在后文说明实现方式。本文档是本次文档维护记录，不新增运行能力，不改变历史验收或发布状态。

## 统一总问题

Agent 能生成一次答案，不等于项目能可靠完成一项长期任务。多轮、多模型、多会话协作时，需求和用户约束会变化，尝试可能失败或超时，产物会被修改，模型也可能把自己的估计当成结果。若这些事实只留在上下文、临时文件或自然语言里，换会话、重试、人工审批和交接后就无法核对做过什么、依据哪一版、为什么选择、谁批准以及外部动作是否真的发生。

Project Kernel 要补的是项目级事实交接、核对和追责能力，不是修复模型的注意力、推理或自然语言理解能力。实现机制、代码入口和验证用例放在架构与当前实现文档中，不作为问题本身的替代描述。

## 12 类问题的记录口径

1. 长上下文注意力丢失：模型对已有上下文的理解逐步偏移，技术债累积；需要知道约束、决策和技术债当时是什么以及后来谁改变了它们。
2. 多对话共同修改：不同会话没有共同事实；需要能核对作者、依据版本、影响模块和冲突状态。当前不是实时协同编辑或自动合并的承诺。
3. 结构设计混乱、文件和产物丢失：需要知道每个产物属于哪次尝试、哪个模块、哪份需求，以及是否可保留或交付。
4. 技能复用差、调用和更新范围不清：需要知道每次复用的 skill 版本、适用条件和来源；新经验经评价、重验和显式晋升后才形成新版本，失败可回滚。
5. 方案不留存、效果与需求定义断链：需要把尝试、失败/未知、选择理由、验收结果和外部效果追到同一需求版本。
6. 操作错误不记录、反复犯错或越过能力边界：需要错误证据、回执、明确未知和明确拒绝，不能把模型自报结果直接当事实。
7. 用户画像和需求约束不明确：需要把用户目标、身份、偏好、知识/权限边界和验收标准作为有来源、有版本的需求输入，不对用户能力评分或自动推断敏感属性。
8. 版本记录和备份不清、改一模块牵全身：需要知道模块、版本、备份和恢复范围的对应关系，判断改动影响和回滚边界。
9. 模型沟通不规范、关键字段被省略：需要需求、验收、版本、失败状态和下一步的最小可核对字段与回执；不把它写成保证自然语言永远完整。
10. 执行过程黑箱、用户没有可视化：需要看到已记录的阶段、依据、拒绝、对比、批准和效果状态；不承诺展示模型内部思考。
11. 长上下文记忆丢失、后续模型不知道原始需求：需要原始需求、用户约束、来源版本、尝试方案和交接摘要可被后续模型引用。它与第 1 类不同：第 1 类是理解偏移，第 11 类是需求上下文本身丢失。
12. 项目与任务双留档不同步或互相锁死：项目级记录保存稳定事实和模块关系，任务级记录保存一次变更的目标、证据和结果；两者通过链接和版本关联，但不互相覆盖。

## 完成口径

- 12 类问题的定义、后果、治理目标和项目/任务双留档分工已完成并写入 README。
- 实现细节、宿主接入方式、部署条件和代码入口由架构与当前实现文档负责，不在问题定义表中重复或冒充问题本身。
- 过程展示、skill 调用、用户约束引用、多会话版本边界和文件归属均纳入同一事实链；具体运行范围按宿主配置执行。
