## 为什么需要项目账本

订单系统把营业日结算从 UTC 改成门店当地时区。第二天换了会话，日报模块还在按旧规则核验跨午夜订单，财务模块已按新规则准备接收结果。聊天摘要即使写着「时区已改」，接手者仍需要追问：改动涉及哪些模块？这项核验实际按哪一版运行？缺少门店时区的订单怎么判？哪份证据支持采用，最终有没有生效？

这几个问题会以不同方式拖慢项目。需求经过多次转述，例外条件容易丢掉。各模块独立推进，局部改动可能改变上下游依赖。日常修改如果每次都走正式审批，会让人把流程当作表格填完。发生重大分歧时，执行者如果同时承担核验和采用，接手人就很难区分「方案试过」与「方案可以用」。会话一结束，证据、分歧和外部副作用还可能散落在三个不同地方。

账本把这些内容留在各自的来源上。项目记录现行需求和模块关系，每项工作固定自己的依据，核验记录实际输入和观察，人工决定关联到当时的候选，外部交付另有回执。下次会话可以接着处理未决问题，也能追查当时的取舍。

## 从一条需求走到交接

1. **先找到受影响模块。** 在 DSH 工作台登记或打开项目，从项目简报看目标、验收条款和模块拓扑。点开结算条款，沿依赖定位订单、财务和日报，再到模块页查看职责、变动、工作与具名对话。比如日报侧只承担归属日展示，日期判定的变更应交回负责结算口径的模块。用 MCP 的团队也可以从项目级概览开始，再按授权读取相关模块和工作。
2. **在原工作里对照两版。** 版本页并列显示这次工作固定的依据（Pinned Basis）与项目现行版本。日报组可以保留按旧版跑出的基线，写明沿用理由。要验证新版，就在明确的版本依据下重跑跨午夜样本。旧回执仍挂在其实际使用的版本上。版本处置结束后可以回到原对话继续编辑，示例演示包括原草稿、焦点和选区恢复。
3. **按这次工作的风险选流程。** 小改动从已有工作或会话开始。只需定设计的工作以范围内的设计结果收尾。跨模块口径采用或需要实际交付时，才由操作者打开正式流程。在具体对话中可关联原生回合、确认成果，并沿方案分支读样本、核验结论及采用记录。可执行动作随宿主配置和授权开放，缺少写入能力时可以把依据与待办交给有权限的接手人。
4. **把样本、采用和交付对上。** 比较「在结算侧计算归属日」与「在日报侧换算」时，核验人会先确认两个候选用的订单和时区条件一致。缺时区的样本保持未知，等待补证。人可以说明理由打回一个候选，保留前次尝试并开出待派发的独立重试。也可以采用已核验的候选，随后沿确切引用回读决定。目标端是否实际收到交付，继续看独立回执。
5. **收尾与复盘回到原处。** 接手人在受影响模块的原始现状记录里读到结论、核验范围和待办。复用「跨午夜样本检查」前，可先看 Skill 的适用条件、反例、正确性、适用性、复用收益和可维护性。复用收益应看可比任务的耗时，缺对照的评分维度保留空项。遇到同类错误，可以沿错误记录跳回原对话，读当时的输入和处置。截图和视频里的 Skill 耗时来自演示样本。

记录工作从所属模块或已指派事项开始。新需求、授权、实质决定，以及会影响后续工作的阻塞或未知操作，应在依赖它们的工作开始前留存。日常记录可以在自然检查点合并。**模块收尾由执行模型做三步**：找到权威现状原文，按已取得的证据更新结论和待验范围，从原入口读回并交给下一位。原文因权限或版本冲突暂时无法更新时，在工作记录注明原因、证据和接手方，标记 `pending_sync`。宿主自动回写仍待验证。 [项目记录 Skill](skills/kernel-maintain-records/SKILL.md)

## 四大路径选择

### 1. 宿主运行助手，账本保存项目事实，人作关键裁决

| 谁负责 | 日常职责 | 遇到问题时找哪里 |
|---|---|---|
| Agent 宿主 | 运行模型和原生工具，管理模型供应商、会话、沙箱与工具权限，执行已授权的宿主操作 | 打开原生对话或宿主日志，查看实际调用及结果 |
| xiaobai 内核与 Skill | 保存项目记录及其精确版本，提供按需读取、写入冲突检查、人审与交付回执 | 从工作台或授权工具打开对应工作，核对版本、证据和状态 |
| 人 | 定目标、边界和验收口径，在可信入口作采用、打回或批准决定 | 核对候选、样本及待验项后，留下决定的理由 |

另一种接入方式是更换整个 Agent 框架，把对话和项目状态收进同一宿主。xiaobai 以独立进程运行，通过标准 MCP stdio 接入兼容客户端，DSH 另有原生项目入口。团队可以继续使用原来的模型、工具和权限体系，接入时需配置独立存储路径、主体和能力。宿主决定何时调用工具，原生工具的执行与恢复仍由宿主负责。工作台里看得到的记录和可提交的动作，取决于宿主授权及已配置的写入方。

### 2. 项目现行版本与工作的固定依据分别记录

聊天摘要或只保留最新版的文档维护起来简单，但同一条测试结论会失去它实际适用的输入。SQLite 账本保留不可变修订，工作里的引用能回到确切记录。提交修改需要提供读取时的版本（CAS）。旧基线发生冲突时，重新读取并核对新旧差异后，再决定如何提交。这要求团队显式处理版本偏移，代价是多一次核对，收益是旧工作和并行修改的依据都能查清。

### 3. 先定位模块，再花上下文预算读原文

一次性把全部资料交给助手，省去了按需查找的调用，但简单任务也要加载完整项目。xiaobai 先给 L0 项目目标、目录和模块关系，再按需取 L1 模块、工作和精确正文。也可用确定性状态卡，在预算内带出相关状态。跨模块核验仍须展开所涉及的关系和原文，预算无法容纳全部依据时，应保留缺口。compact 工具面与分层读取的测量各有样本和口径，详见下方 T1 数据。授权仍由宿主配置，资料目录只是定位入口。

### 4. 让工作按范围进入轻、中、重三种路径

| 路径 | 何时用 | 到哪里算完成 |
|---|---|---|
| **轻：普通工作** | 解释现有口径，补一条局部样本，或在组内讨论一项调整 | 执行者可按简短目标自主计划，无须新建正式任务或额外填一套表单。确认工作成果与实际依据后结束工作，并在有模块现状变动时按三步回写。 |
| **中：仅设计** | 这轮只需要确定营业日规则和验收样本，由后续工作负责实施 | 正式任务已到待派发阶段，有有效的范围确认，且尚无执行、验收或交付事实时，可以用 `task.complete_scoped` 记录设计完成。完成的是本轮设计范围，实施及上线仍各自等待结果。 |
| **重：正式执行与交付** | 涉及跨模块采用、多个候选独立核验，或有正式交付要求 | 由操作者明确启动，确认范围后登记尝试，按需要派发候选、独立核验，随后由可信人类入口作决定，并根据实际交付效果收尾。实际发起交付写入前，内核核对绑定候选与目标的有效批准，应用由配置的交付方负责。 |

统一走重流程便于逐项审计，给日常修正带来的协调成本也高。全部留在自由对话里则省事，但分歧、核验和外部效果难以回读。按风险启用正式流程后，团队仍需判断什么时候升级，并安排独立核验和人工决策。正式链上，Attempt 回答「试了什么」，Verification 回答「独立检查观察到什么」，Approval 回答「人批准了哪份目标与方案」，Delivery 回答「外部实际上发生了什么」。工作台里的采用记录可以先于交付出现。

## 核心创新

沿一次正式工作的记录往回读，可以看到候选为何被打回、采用依据是哪份样本，以及哪一步还在等外部系统回执。

```mermaid
flowchart TD
    A["订单规则 · 固定版本"] --> B["按该版本尝试方案"]
    B --> C["独立核验 · 样本与观察"]
    C --> D{"人工决定"}
    D -->|打回| E["新尝试引用原尝试与理由"]
    E --> C
    D -->|采用| F["已选候选"]
    F --> G["获得交付批准后发起交付"]
    G -->|收到有效回执| H["确认外部效果"]
    G -->|断连且效果未知| I["原键对账"]
    I -->|取得匹配证据| H
```

### 未知效果先对账

如果已发出的交付请求在超时后没有回执，重新写一次也许会追加一份重复制品。xiaobai 将效果留为 `unknown`，用原幂等键和原操作身份查询回执及交付方的观察结果。匹配该操作和摘要的成功证据才能确认效果。仍缺证据时保留未知、等待对账，系统禁止自动重放未知写入。这样会延长个别收尾，但在故障恢复和换会话后，接手者仍能追查最初的操作。

## 校验、安装与接入

使用 Windows x64 和 64 位 CPython 3.12。从同一 Release 下载 [Windows x64 ZIP](https://github.com/LGZX2233/xiaobai2233/releases/download/v0.50.0/xiaobai-v0.50.0-win-x64.zip) 与 [SHA256SUMS.txt](https://github.com/LGZX2233/xiaobai2233/releases/download/v0.50.0/SHA256SUMS.txt)，在 PowerShell 运行 `Get-FileHash ./xiaobai-v0.50.0-win-x64.zip -Algorithm SHA256`，核对清单中同名文件的摘要。打开一个新虚拟环境，在 ZIP 所在目录运行以下三行。

```powershell
Expand-Archive ./xiaobai-v0.50.0-win-x64.zip ./xiaobai-v0.50.0-win-x64
cd ./xiaobai-v0.50.0-win-x64
python -m pip install "project_kernel-0.50.0-cp312-cp312-win_amd64.whl[mcp]"
```

在解压目录也可用随包提供的 `./install.ps1` 完成第三步，它会核对环境和 wheel 摘要，再安装 MCP 依赖并执行 `pip check`。

在支持 MCP stdio 的客户端，将命令指向该虚拟环境的 Python，加载宿主控制的项目配置，完成 initialize 后调用 tools/list。授权范围决定可见工具。DSH 用户可从原生项目入口登记项目并打开工作台。[MCP 配置与 DSH 插件入口](docs/integration.md) · [完整安装说明](docs/release.md) · [v0.50.0 Release](https://github.com/LGZX2233/xiaobai2233/releases/tag/v0.50.0)
